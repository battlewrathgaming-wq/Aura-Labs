## 1. Project Heading

Aura Lab is currently becoming a light, project-local proving bench for an HTML/Electron presentation layer that can display Aura project state with bridge-aware trust language, deterministic fixture modes, visual smoke evidence, and careful text containment. Its value is not to define cross-project product meaning, but to prove reusable presentation mechanics in a low-risk Lab surface before any target-owned Atlas, Sense, or Core adoption path is considered.

## 3. Owned Tool Function

Aura Lab owns a small project-state briefing tool function: presenting a readable Aura project coordination snapshot through the provisional `aura.projectBriefing` bridge and deterministic local test modes.

It currently owns:

- a desktop HTML/Electron briefing surface
- bridge/test state selection for development and review
- source, freshness, certainty, and bridge-state display
- a read-only Needs Attention slice
- secondary diagnostics
- local static/service verification
- local Electron visual smoke with screenshots and JSON evidence

## 4. Owned User-Facing Semantics

Aura Lab owns the semantics of its own briefing surface only:

- Aura Lab project identity
- current focus
- action posture
- Needs Attention
- coordination facts
- Lab fixture labels and copy
- Lab-specific trust and freshness wording as rendered in this prototype

These meanings should not be treated as Atlas evidence doctrine, Sense tactical doctrine, or Aura Core product meaning.

## 5. Shareable Structure Candidates

The following are candidates for shared Aura structure after further review, not accepted shared doctrine yet:

- source/freshness/certainty slots
- primary briefing path before diagnostics

- loading, empty, populated, stale, failed, partial, degraded, unavailable, gated, and blocked states

- renderer/presenter is not truth owner

- action-effect copy that distinguishes read-only, gated, unavailable, and no-effect states

## 8. What Lab Can Safely Model

Aura Lab can safely model fixture-backed presentation behavior:

- how a briefing surface handles good, absent, stale, failed, partial, and long-text data
- how trust, source, freshness, and certainty language sits in the primary reading path
- how diagnostics are demoted without hiding them
- how text behaves in narrow and long-content scenarios
- how visual smoke proves layout health
- how project-local smoke wrappers reduce agent and verification noise

Lab should keep examples neutral or explicitly Lab-native when modeling patterns that might later influence Atlas, Sense, or Core.
