# Portable Face Expansion Support

Status: Reference / Overseer support only
Date: 2026-05-24
Project: Aura Lab

## Purpose

Support Overseer thinking around project expansion as Aura Lab prepares to put developed presentation "faces" onto other Aura projects.

This is not accepted product direction, not a Dev runway, not a bridge contract, and not a target-project adoption claim. It is a framing note for how Lab can mature presentation modules so other projects can later choose to adopt them through their own authority.

## Core Expansion Principle

Aura Lab can develop the face as portable presentation craft.

Target projects own what the face means.

That means Lab can provide:

- visual hierarchy
- information-display modules
- state presentation patterns
- source/freshness/basis affordances
- compact diagnostics treatment
- responsive/narrow-shell behavior
- motion language
- HTML/CSS/JS implementation patterns when accepted later

Lab must not provide, on behalf of a target project:

- product doctrine
- backend truth semantics
- source-project field meaning
- evidence or threat claims
- durable bridge contracts
- target-specific labels unless reviewed by that target
- automatic adoption authority

## What "Face" Should Mean In Lab

In Lab language, a face should mean:

```txt
A visible presentation treatment for bridge-fed information that makes state, source, freshness, basis, and next useful attention clear at a glance.
```

A face should not mean:

```txt
A universal product skin that overwrites a target project's language or meaning.
```

The face is the presentation layer. It can be beautiful, tactile, animated, and expressive, but it must remain honest about the information it is showing.

## Expansion Model

Recommended mental model:

```txt
Source Project Meaning
        ↓
Bridge / Snapshot / Read Model
        ↓
Lab Presentation Face Pattern
        ↓
Target-Owned Adoption Review
        ↓
Target Implementation
```

Lab should focus on the middle presentation face pattern. The target project should review meaning, labels, adoption fit, and any required contract changes.

## Portable Face Ingredients

A mature Lab face should eventually include:

- first-read hierarchy
- state grammar
- freshness treatment
- source/basis treatment
- degraded/partial/failed treatment
- empty/loading treatment
- compact diagnostic treatment
- motion behavior
- narrow layout behavior
- typography and density rules
- surface/material rules
- accessibility and reduced-motion notes
- terminology risk notes
- target-review questions

These ingredients can travel without pretending that all projects mean the same thing.

## Presentation Modules That Can Travel

Strong candidates for portable Lab modules:

- Status Light Grammar
- Source/Freshness Strip
- Readout Basis Line
- Tactical/Instrument Signal Band
- Rolling Counter / Telemetry Reel
- Activity Timeline
- Compact Diagnostics Panel
- Detail Drawer
- Partial/Stale/Failed State Panel
- Last-Known / Fallback Treatment
- Comparison Readout
- Narrow Overlay Shell

Each module should be designed so labels and data meaning can be supplied by the target project.

## What Must Be Parameterized

Portable modules should allow target projects to own:

- visible label text
- state names
- severity mapping
- source names
- freshness thresholds
- basis wording
- warning language
- empty-state copy
- action labels
- whether a module is primary or secondary

Lab can recommend default neutral copy for Lab fixtures, but those defaults must not be mistaken for target-project authority.

## What Can Be Shared Safely

Safer shared affordances:

- typography scale
- spacing rhythm
- panel structure
- rail/strip/drawer geometry
- light/pip/bar components
- loading sweep behavior
- brief transition timing
- stale dimming behavior
- reduced-motion fallback
- truncation and overflow rules
- diagnostic demotion strategy
- source/freshness placement conventions

These are presentation behaviors, not meaning claims.

## Face Families Vs Target Faces

Lab can explore face families such as:

- instrument face
- tactical face
- low-emission terminal face
- activity face
- evidence-adaptable face
- sensor face

But target projects should own target faces, such as:

- Sense face
- Atlas face
- any future project-specific face

Lab can provide patterns and prototypes. Target projects decide whether a pattern fits.

## Overseer Expansion Questions

Useful questions for Overseer before shaping expansion milestones:

- Is this module useful as a presentation pattern even without a target project?
- Does it depend on target-owned semantics?
- Can it be demonstrated with neutral fixture data?
- Can target-specific labels be swapped without breaking the design?
- Does it clarify source, freshness, basis, and state?
- Does it remain readable in a narrow shell?
- Does it create accidental claims of authority, proof, confidence, threat, or evidence?
- Is the motion meaningful without being required?
- Does this help a target project adopt a face later with less design debt?
- What target-owner review would be required before adoption?

## Suggested Expansion Path

This is not a Dev runway. It is a possible sequencing model for Overseer.

### Phase 1: Lab Face Concept Pack

Goal:

- Decide which portable presentation module should be prototyped next.

Output:

- concept ranking
- selected smallest prototype
- terminology risk
- data/fixture needs
- acceptance checks

### Phase 2: Lab Prototype

Goal:

- Build one visible HTML presentation module using neutral fixture data.

Output:

- working Lab prototype
- state coverage
- screenshot evidence only as support
- notes on what is portable and what is fixture-only

### Phase 3: Face Transfer Review

Goal:

- Review whether the module can be adapted by a target project.

Output:

- target-facing advisory
- target-owned terminology questions
- required target-contract questions
- adoption risks

### Phase 4: Target-Owned Adoption

Goal:

- Target project decides whether and how to adopt.

Output:

- target-local runway
- target-local implementation
- target-local verification

Lab should not skip directly from Phase 2 to target implementation.

- choose one smallest safe prototype
- identify what can become portable
- identify what must stay Lab-only

## Target Project Cautions

### Sense

Sense is transient, tactical, lane-bound, and backend-truth-owned.

Lab-inspired face work can help Sense visually, but Sense owns:

- lane names
- combat/telemetry/threat meanings
- live IO language
- bridge snapshots
- backend truth
- tactical state semantics

Lab should not import Sense tactical labels as Lab defaults.

### Atlas

Atlas is durable evidence/investigation memory.

Lab-inspired face work can help Atlas visually, but Atlas owns:

- evidence semantics
- report/watch/storage/assessment language
- historical meaning
- provenance meaning
- actor/activity interpretation

Lab should not make generic Lab activity/timeline modules look like Atlas evidence unless Atlas accepts that framing.

### Core

Core should not become the owner of Lab face doctrine by accident.

Lab uses inherited scaffold rigging, but Lab owns its own presentation exploration.

## Expansion Risks

- The face becomes a skin instead of a presentation system.
- Target projects inherit Lab fixture language by accident.
- Lab starts defining bridge contracts while trying to make modules portable.
- References become hidden requirements.
- Verification grammar overtakes visual/product exploration.
- The first target adoption overfits the face to one project.
- Tactical styling creates false authority or urgency.
- Beautiful surface treatment hides stale, partial, failed, or missing data.

## Guardrails For Expansion

- Keep Lab prototypes source-agnostic.
- Keep target meanings target-owned.
- Keep references in `workspace/reference/`.
- Keep accepted direction in `workspace/current.md`.
- Keep durable project truth in `docs/` only when accepted.
- Treat target adoption as a separate target-owned milestone.
- Prefer neutral fixture data for Lab prototypes.
- Use target project reads only to understand constraints, not to define their direction.
