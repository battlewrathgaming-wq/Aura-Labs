# Display Asset Documentation Owner Contract

Status: Active Lab workflow contract
Date: 2026-05-25
Owner role: UI development owner / presentation systems specialist

## Purpose

Define how a UI development owner may lead Aura Lab display asset documentation and workshop productivity hardening.

This contract gives the UI development owner clear responsibility for making the display asset inventory useful. It does not transfer Lab product direction, milestone authority, target-project adoption, or source-project meaning ownership.

## Role Definition

The UI development owner owns the practical documentation system for Lab display assets.

Their mandate:

```txt
Make future Lab UI work easier to discover, understand, extend, verify, and adapt safely.
```

They may own:

- display asset page shape
- display inventory usefulness
- workshop-to-inventory graduation proposal
- metadata needed by UI/UX, Dev, and Overseer
- screenshot/example conventions
- display material needs
- productivity hardening around finding, extending, and reusing display elements
- proposed documentation workflow for asset updates

They do not own:

- Lab product direction
- milestone acceptance
- `workspace/current.md`
- Dev runways
- target-project adoption
- Atlas, Sense, or Core meaning
- durable bridge contracts
- shared Aura doctrine
- shared protected-word JSON

## Workflow

1. Review accepted Lab authority and current project state.
2. Review the existing display asset proposal, workshop README, reference folder, and M19 current-state note.
3. Propose or refine the display asset documentation system.
4. Keep the work advisory unless `workspace/current.md` explicitly opens implementation or documentation execution.
5. Route acceptance through Overseer.
6. If accepted into `workspace/current.md`, create or update only the named docs/artifacts.
7. Leave inventory-ready facts for Dev or Overseer when implementation happens outside the documentation owner packet.

## Expected Work Product

A useful UI development owner artifact should answer:

- What counts as a display asset?
- What metadata does every asset need?
- Where does the inventory live?
- What is the minimum useful asset page?
- What is too much process?
- How are screenshots/examples referenced?
- What verification/support belongs on an asset page?
- How does a Dev handoff feed inventory updates?
- How does a workshop idea become proposed, in progress, accepted, parked, or retired?
- What remains Human-owned?
- What remains Overseer-owned?

## Acceptance Bar

Overseer may accept the work if it:

- makes future Lab UI work more productive
- stays practical and short enough to use
- supports display elements rather than broad product faces
- preserves Lab-owned default vocabulary
- keeps target-project meaning target-owned
- avoids hidden backlog behavior
- avoids glossary or bridge-contract drift
- names what future Dev packets need without opening them directly

## Documentation Rules

- Keep inventory pages concise.
- Link to authority instead of copying long term lists.
- Use `Verification / Support`, not higher-authority wording.
- Treat screenshots as examples, not acceptance.
- Treat reference material as inspiration or display pressure, not requirements.
- Do not create asset pages for every CSS class.
- Do not fill unknown metadata with invented detail.
- Do not write target-project adoption claims.
- Do not update shared protected-word JSON.

## Ownership Boundary

Human owns:

- vision
- priority
- acceptance
- whether an asset is worth pursuing
- larger strategic moves

Overseer owns:

- milestone boundaries
- `workspace/current.md`
- acceptance, redirect, park, or retire decisions
- whether docs become durable project knowledge
- whether target-project review is appropriate

Dev owns:

- implementation only when assigned by `workspace/current.md`
- verification and implementation handoff facts

UI development owner owns:

- display asset documentation mechanics
- inventory usability
- workflow proposals for workshop-to-inventory movement
- productivity hardening for future UI workers

## Stop Conditions

Stop and return to Human / Overseer if:

- the work would create or modify a Dev runway
- the documentation starts deciding product direction
- a display asset requires source-project meaning decisions
- target-project labels are needed as Lab defaults
- display material begins acting like a bridge contract
- a workshop idea becomes a hidden backlog item
- the process becomes heavier than the asset work it supports
